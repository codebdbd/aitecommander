# Cache Style Guide (Project-wide)

Цель: определить единые правила кэширования в проекте, чтобы повысить предсказуемость, наблюдаемость и устойчивость.

## Базовые принципы

- **Кэш — не источник истины.** Всегда должен существовать безопасный путь получения данных из модели/сервиса при MISS или ошибке кэша.
- **Консервативный TTL.** Значения кэша не должны «залипать» навсегда. По умолчанию используем небольшой TTL (например, 600 секунд), если нет причин хранить дольше.
- **Чёткие ключи.** Формат ключа должен отражать контекст (сферу/раздел/категорию) и назначение.
- **Явная инвалидация.** При изменениях данных кэш должен инвалидироваться точечно и/или в соответствующих агрегатах.
- **Диагностика.** Важно логировать HIT/MISS/SET для «чувствительных» ключей в DEBUG-режиме.

## Форматы ключей

- Пер‑сфера «первая категория/раздел»:
  - `first_category_id:{sphere_id}` — ID первой доступной категории для сферы
  - Используется в `UtilityService.get_target_section_id()` и прогревается после загрузки структуры.
- Структура и списки:
  - `structure_{sphere_id}` — полная структура сферы
  - `sections_{sphere_id}` — список разделов для сферы
  - `categories_{section_id}` — список категорий для раздела

## Инвалидация

- На уровне бизнес‑логики (`StructureBusinessLogic`):
  - `_invalidate_structure_cache()` сбрасывает:
    - `structure_{sphere_id}`
    - `sections_{sphere_id}`
    - `first_category_id:{sphere_id}` (унифицированный формат)
  - `_invalidate_categories_cache(section_id)` сбрасывает `categories_{section_id}` и повторно вызывает `_invalidate_structure_cache()`.

## TTL и хранилище

- `CacheManager` использует универсальный `InMemoryCache` с **дефолтным TTL = 600 сек** (10 минут), если не указан явно при инициализации.
- TTL можно переопределить через параметр конструктора `CacheManager(ttl=...)` при необходимости.

## Прогрев кэша

- После загрузки структуры (`StructureBusinessLogic.structure_loaded`) выполняется **лёгкий прогрев** per‑sphere ключа `first_category_id:{sphere_id}` в слоте `_on_structure_loaded_warm_cache`.
- Прогрев не блокирует UI и использует уже кэшированные списки разделов/категорий, если они доступны.

## Диагностика и логирование

- В `UtilityService.get_target_section_id()` включены DEBUG‑логи событий HIT/MISS/SET для ключа `first_category_id:{sphere_id}`.
- Рекомендуется держать уровень логирования INFO/ERROR в продакшене и включать DEBUG только при диагностике проблем.

## Рекомендации по использованию

- При наличии контекста сферы используйте per‑sphere ключи и методы `CacheManager` (или универсальные `get/set` с указанным форматом ключа).
- Для глобальных сценариев допускается использовать отдельные ключи (например, `first_category_id`), но по возможности отдавайте предпочтение per‑context ключам.

## Пример использования (пер‑сфера «первая категория»)

```python
# Чтение с кэшированием
key = f"first_category_id:{sphere_id}"
value = cache.get(key)
if value is None:
    value = compute_first_category_id_for_sphere(sphere_id)
    cache.set(key, value)  # TTL берётся по умолчанию
return value
```

## CI контроль (grep‑чек для SQL)

- В CI должен быть шаг проверки недопустимого позиционного доступа к SQL‑результатам в `app/models/`.
- Ищем шаблон `\[[0-9]+\]` и падаем, если найден в модельном слое. Идея — не допустить `row[0]` и подобных конструкций при чтении результатов запросов.
- См. `.github/workflows/sql_positional_check.yml` для готового шага.
